## The proposal under evaluation (Option A)

> Anchor + disposition ledger = append-only JSONL committed under `substrate/ledger/` in
> `github.com/christianpiatt-jpg/clarityos-runtime.git` @ `main`.

**Rationale.** Anchor authority is intrinsically tied to git HEAD (A131), so committing the
ledger keeps anchors and the code they cite atomically versioned, with free history, diff,
and review. Git already survives any agent/container reset.

## The boundary CT-2 must weigh

Git-as-ledger fits the **team/dev plane** (anchors minted by CT-1/CT-2/CT-3/COW working in the
repo). It does **not** fit **runtime minting**: a Cloud Run request handler cannot cleanly
commit + push, so any ledger entry generated by the live service would have no path into git.
CT-1 has deferred the runtime write handler to a separate task — so for now the ledger is
team-plane-only, which is exactly where this command structure operates. The question is
whether that boundary is acceptable, or whether anticipated runtime minting argues for a
runtime-writable store instead.

## Evaluation questions for CT-2

1. **Store choice.** Given the runtime can't write to git, is Option A (git) right for now, or
   does expected runtime minting push toward Option B (Firestore/GCS)?
2. **Concurrency.** Multiple agents appending JSONL → merge conflicts. Mitigation — single
   writer? per-agent files? a serialized commit path through CT-3?
3. **Commit/push discipline.** Which identity commits, at what cadence, signed? (Ties to R-9,
   unsigned-directive invalidity.)
4. **Format.** One `ledger.jsonl`, or split `anchors.jsonl` / `dispositions.jsonl`?
5. **Projection.** Keep the canonical ledger in git but project a read-only mirror to Firestore
   for runtime reads (best of both)? This would also serve the CT-3 compiler.
